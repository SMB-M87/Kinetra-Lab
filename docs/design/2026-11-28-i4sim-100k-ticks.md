## Problem

Profiled on 2026-11-28 on Lab `8b1115e` with Kinetra `1dd9c83` ([how](../performance.md#how-to-measure)): `kinetra_i4sim --blueprint labs/i4sim/blueprints/3840x2400.json --ticks 1000000 --seed 42`, 72,400–75,600 ticks per second in three runs.

| Where | Self | Why |
| --- | --- | --- |
| `MotionStep::resolve_contacts` | 30% | For every mover, the distance to every border of the floor, in every tick ([motion_step.cpp](../../labs/i4sim/src/simulation/motion_step.cpp)); hotspot 8 removed the same loop from `surroundings`, the performance page's open points named this one |
| `Production::update` | 12% with what it calls | Every waiting product, every tick, tests every producer, and `recipe()` returns a new vector on each call |
| `kinetra::bounds` | 9.5% with what it calls | Computed again every tick for every mover, also for the ones that stand still |
| Allocation and freeing | 3–6% | `run()` and `resolve_contacts()` build their snapshot, bounds, mover index and contact set anew every tick; the stall and right-of-way observations their mover lists |

After the first change, the border query itself was 11% of the run: most of the 25 movers stand at a producer or a parking place, and their position, so the borders near them, is the same from tick to tick.

## Goals and non-goals

Goals: `3840x2400` at 100,000 or more headless ticks per second on the cloud machine, measured as the median of interleaved runs; every result unchanged (the summaries, the benchmark's columns but the times, the golden lines).

Non-goals: `8640x4800`, where the pairs of 106 movers and steering dominate; engine changes (Kinetra's `SpatialGrid::cells`, `StallDetector`'s legs and `validate`, which are now large shares); the open choice of when to compute the diagnostic forces of `priority_steer`.

## Decisions

| Decision | Choice | Why |
| --- | --- | --- |
| Which target | `3840x2400` at 100,000 ticks per second, headless | The user's choice on 2026-11-28, from four options: this floor, the next step without a figure, `8640x4800`, or 100,000 UPS in the window |
| Exact or approximate | Exact | Every change keeps the order of the work and its arithmetic, so no result needs a new baseline |
| Repository | Lab only | Enough for the target; the engine shares stay on the roadmap item, so no Kinetra pull request and no pointer move |
| Remembering per mover | The border list and the box of a mover, by its position and extents (and angle for the box) | Both are pure functions of those fields and of the floor, which never changes, so a stale entry can only be one with other fields, which is computed again |

## Design

1. **Borders of a contact through the index.** `resolve_contacts` asks `FloorPlan::border_index()` for the borders around the mover, as `surroundings` does since hotspot 8, and keeps the same distance test. The query square is the contact reach (`length(half_extents) + 0.01`) widened by `border_search_margin_mm`, so it holds every border the test accepts, in ascending order.
2. **Supporting producers once.** `Production` lists, per interaction, the producers whose model supports it, when it is made; `schedule()` visits only those, in ascending order, so it chooses the same producer. `recipe()` returns a `std::span` over static arrays instead of a new vector.
3. **Buffers kept across ticks.** `MotionStep` keeps the snapshot, the bounds, the mover index (made again only when the floor's cell size differs), the bodies and bounds of contact resolution, and the touching pairs. The pairs are found in ascending order, every mover pair `(i, j > i)` before `i`'s borders `(i, movers + j)`, so they are a sorted vector without sorting, searched with `std::binary_search` instead of a `std::set`. The stall and right-of-way observations keep their mover lists too.
4. **Near borders remembered per mover.** `MotionStep::near_borders` keeps, per mover, the position and extents it last searched for and the borders the distance test accepted. A mover that stands still skips the query.
5. **Boxes remembered per mover.** `MotionStep::box_of` keeps a box mover's position, extents, angle and `kinetra::bounds`; `run()` and `resolve_contacts()` use it. Other shapes are computed as before.

## Verification

On 2026-11-28, `release` preset (GCC 13.3), cloud machine with four cores:

- Every step, before the next: the ten summaries byte-identical to `main`'s.
- `ctest --preset dev -R '^kinetra_i4sim'`: 191 of 191 (the three benchmark-argument tests after building `kinetra_i4sim_motion_benchmark` in `dev`).
- `kinetra_i4sim_motion_benchmark --ticks 50000` in the seven modes of the test plan: all columns but the times equal.
- The target, `main` and the branch interleaved, three runs each, medians: `kinetra_i4sim --blueprint 3840x2400.json --ticks 1000000 --seed 42` from 72,000 to 108,500 ticks per second (−34% in time); `test-environment` from 241,000 to 332,000; `8640x4800` at 200,000 ticks from 9,500 to 10,100. Per step, interleaved with the step before (five runs, medians, on a machine whose rate varied by up to 10% between series): border index 72,400–75,600 → 79,400–85,500 (three runs each, not interleaved), with the supporting producers 71,200 → 91,600 against `main`, buffers 88,300 → 96,900, near borders 90,900 → 99,400, boxes 98,200 → 105,500.
- `kinetra_i4sim_motion_benchmark --ticks 50000`, three runs each, interleaved: default from 10.9 s to 10.0 s (−9%), with `--predictive-passing` from 25.0 s to 23.7 s (−5%); `8640x4800` takes most of both.
- `clang-format`, `check_docs.py`, `check_copies.py`.

## Open points

- Kinetra's shares are now the largest after steering: `SpatialGrid::cells` about 12% (its four double divisions and checks, in every query and rebuild), `kinetra::validate` 8%, and `StallDetector::observe` 7–8% with `legs_of`, which computes every mover's footprint every tick although only a new stall episode reads them. They belong to Kinetra's hotspot item.
- The i4sim row of [verification in Lab](../../AGENTS.md#verification-in-lab) leaves out `kinetra_i4sim_motion_benchmark`, while its regex `^kinetra_i4sim` selects the three `kinetra_i4sim_benchmark_*` tests that run it: built as the row says, two fail and one does not run.
- `8640x4800` gains little (about 11,000 to 11,400 ticks per second at 50,000 ticks): there the pairs of 106 movers and steering dominate, as before.
